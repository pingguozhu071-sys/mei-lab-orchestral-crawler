# 技术白皮书

本文说明这套引擎要解决什么问题、用什么结构解決、每个选择付出了什么代价,
以及哪些问题至今没解决。

面向的读者是准备读代码或扩展它的人。使用说明在 [README](../README.zh-CN.md),
模块细节在 [架构](ARCHITECTURE.md)。

---

## 1. 问题

网页采集的失效不在「能不能发出一个请求」,而在五类反复出现的问题。

### 1.1 内容取不到

同一个页面,换个客户端就取不到:有的站点校验 TLS 指纹,有的要求执行 JavaScript
才吐出正文,有的对频率和访问轨迹做联合判定。任何单一策略都会在某类站点上失效。

### 1.2 并发写坏

同一页面被两个执行单元同时处理,结果互相覆盖;或者一个单元崩溃后任务永久停在
「处理中」,再也没人接手。这类问题往往**静默**:日志没有异常,统计看起来正常,
只是某些页面永远缺失。

### 1.3 产物不干净

重复内容、空壳页(导航栏 + 广告位,没有正文)、混进正文的第三方手机号与邮箱、
带着会话令牌的 URL。其中 URL 签名参数有一个反直觉的性质:**它不能从任务队列里抹掉**,
因为下一次请求还要用它,抹了就直接 403。

### 1.4 存活崩塌

一个挂死的页面拖住整批任务;限流与重试设计不当会形成重试风暴,越重试越被限流。

### 1.5 媒体取不到

媒体直链通常藏在页面内嵌 JSON 里,带时效签名;大文件下载还需要断点续传与字节校验。

## 2. 解法

针对上面五类问题,引擎分六层应对。每层都只解决一件事。

### 2.1 可达性层:两层通道 + 一次升级

通道按成本排序:

1. **HTTP 通道** —— curl_cffi 发起请求,带浏览器级 TLS 指纹
2. **浏览器通道** —— 每个 Worker 一个独立 Chromium,注入设备档案

嗅探在路由之前离线完成,不联网。它被允许朝「便宜」的方向猜错:猜成静态 HTML
但实际需要 JS 渲染,代价是一次浪费的 HTTP 请求;猜成需要浏览器但其实是静态页,
代价是一个几十倍的浏览器启动。前者可以接受,后者不行。

猜错的补偿机制是**升级**:HTTP 通道拿回的页面如果提取到的正文近乎为空,
任务重新入队,打上 `escalate=browser` 标记,再走一次浏览器通道。只升级一次。

`https://quotes.toscrape.com/js/` 上:HTTP 通道 29 字符,升级后 1,429 字符。

### 2.2 一致性层:租约 + CAS

`tasks` 表带三个字段:`leased_at`、`lease_expires`、`worker_id`。

- 领取时在**同一条 `UPDATE … RETURNING`** 里完成「选中 + 置 running + 写租约」,
  并发领取不会拿到同一条任务。
- 长任务执行期间续租。默认租约 120 秒。
- 完成时做 CAS:租约时间戳必须仍是自己领到的那个,否则说明任务已被别人接管,
  本次结果丢弃。
- 每一轮把过期租约收回 `pending`。

这样做的代价是需要维护租约时长——设太短会误回收正在跑的任务,设太长会让崩溃的
任务卡更久。120 秒是在「单页通常 2–5 秒」这个实测基础上留出的余量。

### 2.3 流控层:四重限速

取四者最大值再发请求:最小间隔(1.5 秒)、随机抖动、robots 的 `Crawl-delay`、
域名冷却截止时间。

429 单独处理:按 `Retry-After` 退避(上限 300 秒),给该域名设冷却,
并且**不消耗主重试次数**——被限流不是任务本身的错,让它和真正的网络失败共用
重试预算会导致任务在限流风暴中被判死。

### 2.4 出口安全层:逐跳 SSRF 闸

所有出网路径共用 `workers/base.py` 里的 `check_url_safe()`:

1. 协议白名单(只 http/https)
2. 主机名规范化(去 IPv6 zone id、去 FQDN 尾点)
3. 数字字面量主机名还原(十进制 / 十六进制 / 八进制 / 省略段)
4. DNS 解析后逐个 IP 判定,判定结果缓存 90 秒(阻断 rebinding)
5. 拒绝环回、私网、链路本地、保留、多播,以及标准库没覆盖的
   `100.64.0.0/10`(CGNAT)、`192.88.99.0/24`、`198.18.0.0/15`、`240.0.0.0/4`、`0.0.0.0/8`

重定向不交给 HTTP 客户端自动跟随,而是手动逐跳处理,每一跳重新过一遍上面的检查,
最多 10 跳。播放列表、m3u8 分片、媒体直链、RSS 源全部复用这一个闸。

代价是热路径上多一次 DNS 查询和若干次 IP 判定。缓存把主要开销压掉了。

### 2.5 数据卫生层:三层脱敏

| 层 | 位置 | 做法 |
|---|---|---|
| 日志层 | `logging.Handler` 上的 filter | 替换消息与参数里的敏感串 |
| 旁路层 | CLI 输出、异常回显 | 统一走 `sanitize_out()` |
| 产物层 | 导出前 | 整条记录递归脱敏(深度 6) |

覆盖手机号、邮箱、IPv4,以及 19 类敏感 URL 参数(token / sign / w_rid …)。

**明确的例外**:任务队列里的 URL 不脱敏。它是后续请求的凭据。这条边界写在代码里,
不依赖人记住。

### 2.6 媒体层:三条路径,一个出口

`.m3u8` 直链 → 自研 HLS 下载器;平台页面 → 平台解析器 → 自研直链下载器;
其余 → 通用 yt-dlp 通道。三者都产出 `MediaItem`,下游不关心来源。

断点续传在两层实现:直链用 `Range` 请求 + `.part` + 原子改名 + 字节校验;
m3u8 用 `.state.json` 记录已完成分片数与字节数。yt-dlp 的续传由它自己管理,
框架只用「目录快照差集」认定产物——`.part` / `.ytdl` 是中间态,不算成果。

## 3. 设计取舍

### 3.1 多进程而非 asyncio

这是与姊妹工程最大的分歧。kiana-crawler 走 asyncio 单进程,理由是协程开销低、
共享状态方便。本工程选多进程:

- 浏览器实例天然需要独立进程,一个 Chromium 崩了不该带走整个引擎
- 阻塞调用(yt-dlp 子进程、OpenCV、文件写入)在协程模型里要么 `to_thread`
  要么堵事件循环
- 进程间隔离让「一个 Worker 崩溃」变成可观测事件而不是级联故障

代价是:跨进程只能传可 pickle 的对象;Windows spawn 下同步原语不能放在
`Process` 子类实例属性上(见经验记录 G-03);父进程与子进程之间的数据往返有序列化成本。

### 3.2 单机单用户,明确不做分布式

不做 Redis、不做多租户、不做一致性哈希。目标场景是「一台机器跑一批 URL」,
分布式带来的复杂度在这里没有回报。`redis_frontier` 这类实验性设计不做。

### 3.3 平台解析器只做一家,其余委托 yt-dlp

抖音、小红书、快手、网易云的直链需要请求签名,签名算法随平台更新而失效。
自研签名器意味着持续逆向,且失效时是硬失败。

B 站不同:它有稳定的公开 API,而且 CDN 支持 Range。所以 B 站走原生 API,
其余四家交给 yt-dlp(它自己维护这些 extractor)。

这个取舍的代价是:这四家的解析质量取决于 yt-dlp 的版本。收益是零维护成本,
且失败时还有通用通道兜底。

### 3.4 静态规则与启发式并存

站点规则能精确抽取,但需要人工编写;密度启发式什么站点都能跑,但字段名不可控。

引擎的处理是:规则命中就覆盖启发式,规则不命中就退回启发式。规则不匹配不报错。
这让「加一个站点」变成可选的优化,而不是必须的前置工作。

### 3.5 质量闸拒收,而不是降级入库

正文过短、链接密度过高的页面被判低质量,不写进仓库。空壳页(有脚本、正文极短)
先尝试升级通道,升级后仍不合格则拒收。

宁可少一个页面,也不要让「加载失败页」污染结果集——一旦污染,后续的所有统计和
去重都建立在错数据上。

### 3.6 指纹注入发生在加载之后

这不是选择,是约束。Patchright 1.61.2 不执行 `add_init_script`,
也不认 `route.fulfill` 改写过的 HTML(经验记录 G-01)。引擎启动时探测这个能力,
不支持就把注入挪到加载后。

已知代价:对「页面脚本一加载就采集指纹」的站点,原生值仍会露出。要文档级注入
得切官方 Playwright,代价是暴露 CDP 调试器。这个取舍没有免费选项。

## 5. 已知架构债

按「需要什么才能关闭」分类。

### 5.1 需要产品决策

**七个文件超过 300 行。** `engine.py`、`core/queue.py`、`workers/http.py`、
`media/resolvers.py`、`stealth/profiles.py`、`stealth/behavior.py`、
`media/m3u8_downloader.py`。

它们已冻结——新能力进新模块。但拆分的边界需要一个判断:比如 `engine.py` 里的
「任务生命周期」与「结果处理」是否应该分开。这取决于以后是否要支持多队列,
现在没有依据,所以不动。

### 5.2 需要真实样本

**媒体通道的完整性校验依赖服务端提供长度。** 服务端不返回 `Content-Length` 时,
截断传输无法被发现。要收紧这一条,需要一批真实的、故意截断的 CDN 样本。

**加密媒体流目前只以 HTTP 状态码判断分片成功。** 空响应、截断内容、软错误页
都可能被当成成功分片。同样需要真实样本才能定验收标准。

### 5.3 需要时间积累

**覆盖率只报告不设阈值。** 现在设阈值只会诱导写「凑覆盖率」的测试。
等事故回归用例积累到一定规模,阈值才有意义。

**站点规则只有 3 条。** 机制完整,资产为零。扩到覆盖主流站点需要持续投入,
且规则会随站点改版失效,需要维护节奏。

### 5.4 结构性限制

**Patchright 下注入只在加载后。** 见 §3.6。

**B 站评论匿名不可读。** 平台限制,只能靠用户自备 cookie。

**没有 GUI。** `mel shell` 覆盖了日常交互,但任务列表、进度视图这类需要窗口的
东西没有。这是形态选择,不是缺陷——但确实是功能缺口。

**没有代理出口管理。** 需要代理基础设施,当前需求没有提出。如果以后要做,
最小可用的版本是「按域名强制直连」这类规则。

### 5.5 已登记但不修

**`Episode.rounds_runned` 拼写。** 采集自工程书原文,改动会破坏既有数据契约。
在 docstring 里标注了。

**`DeviceProfile` 的 `mobile` 与 `is_mobile` 双字段。** 两者语义可能不同
(一个是业务含义,一个是 Playwright 的 context 参数),并存并在 validator 里
同步校验。合并需要先确认所有调用点,收益不抵风险。

## 6. 方法论

这个工程在实现过程中反复用到四条判据。它们来自 kiana 的整改记录,但在本工程
独立验证过一遍。

**判据必须查结构,不许查文本。** 验证码检测最初用裸字符串匹配,结果 B 站每页
预加载的 `risk-captcha-sdk/CaptchaLoader.js` 被误判成拦截(经验记录 G-07)。
改为剔除 `<script>` 段后只查脚本外的组件容器,误报消失。

**「没有告警」不等于「通过」。** 指纹注入是否生效,不能看日志有没有报错,
得在 `about:blank` 上实测一次并留下布尔状态(`_init_script_supported`)。

**复核命令必须真能跑出它上面的数字。** 本文第 4 节的数字由脚本生成;
`docs/` 里的每条实测结论都附命令。

**计数口径必须与被移动的状态同源。** 修「升级吃预算」那个 bug 时,
本质是「已处理数」与实际进入终态的任务数不同源(经验记录 G-11)。
把 `_handle_result` 的返回值改成「是否终态」之后,两个口径对齐了。

## 7. 边界声明

引擎面向公开内容的采集。以下行为不在范围内,也不通过配置开启:

- 绕过登录墙、付费墙、账号权限
- 破解验证码以越过访问控制(验证码识别仅用于**已知可公开访问**页面上的挑战)
- 未脱敏的个人信息落盘
- 多用户、多租户、对外提供服务

依赖清单与合规说明见 [来源与合规声明](COMPLIANCE.md)。
